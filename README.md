# Trend Watcher — Stateful Multi-Observation Skill with Persistent Memory

**Pharos Atlantic Testnet · chainId `688689` · Next.js 15 (App Router) · TypeScript strict · viem · wagmi v2 · Vitest**

A production-grade autonomous agent skill that watches a metric **once per cold-started OS process**, persists every observation to **disk** (never RAM), enforces a configurable **≥ 3-consecutive-observation trend rule** before acting, **rejects single spikes** (flash-loan / oracle-manipulation noise), and — only at the exact confirmed trigger moment — executes a **real on-chain protective action on Pharos Atlantic Testnet carrying a cryptographic Proof-of-Trend**.

> **Reviewer shortcut:** run `npm run watcher:verify` to reproduce every claim below, `npm test` for the 267-test suite, `npm run dev` for the interactive console.

## 🧠 The four high-scoring innovations

| # | Innovation | Where | What it does |
| --- | --- | --- | --- |
| 1 | **Hash-chained observation log + on-chain Proof-of-Trend anchor** | `src/lib/observation.ts`, `src/lib/proof.ts`, `contracts/TrendAnchor.sol`, `src/lib/chain.ts` | Every observation commits to its predecessor: `hash_i = keccak256(hash_{i-1}, blockNumber_i, value_i, observationId_i)`. At trigger, `trendProofDigest = keccak256(ruleHash, windowObservationHashes[])` is **embedded on Pharos Atlantic** (`TrendAnchor` contract event + storage, or native calldata fallback) — proving on-chain exactly *which sequence of observations* authorized the agent. Any tampering with the on-disk history breaks the chain and the store **refuses to act**. |
| 2 | **Z-score / MAD outlier & whip-saw filter** | `src/lib/outliers.ts` | Rolling Median Absolute Deviation over the last 8 per-check deltas (robust z-score ≥ 3.5) plus an absolute bps threshold distinguishes flash-loan / single-block oracle spikes from genuine structural trends. A spike can never *anchor* a confirmed streak; if the next check recovers → `SPIKE_REJECTED`, streak zeroed, no action. |
| 3 | **Multi-process cold-start CLI harness** | `scripts/run-check.ts`, `scripts/lib/spawn-check.ts`, `tests/cli.test.ts` | Every observation is produced by a **brand-new OS process** (`spawnSync` via tsx, fresh PID). The suite and the verifier prove mathematically that zero state lives in RAM: PIDs differ per check, SIGKILL mid-run loses nothing (WAL replay), replayed blocks are deduplicated by the deterministic idempotency key. |
| 4 | **Epoch cooldown & hysteresis guard** | `src/lib/storage.ts` (`ACTED_LOCKED`), tested in `tests/runcheck.test.ts` | After an on-chain action the watcher enters a configurable cooldown: subsequent readings are stored as `COOLDOWN` (streak frozen to 0) and can **never** fire a duplicate transaction — even mid-downtrend with a full new streak. A fresh full trend is required after expiry. Proven live in Phase C. |

## 🔱 On-chain action design

When the rule fires, `executeProtectiveAction()` (mode `auto` by default):

1. Deploys (once, cached in `.data/watcher-<id>/anchor-contract.json`) or reuses the **`TrendAnchor`** contract and calls
   `anchor(ruleHash, proofDigest, triggerIndex, windowObservationHashes)` — emitting `TrendAnchored` with the complete window; or
2. **Fallback:** a native PHRS self-transfer whose calldata carries the ABI-encoded proof (visible on PharosScan input data).

The action tx hash is written into the persisted `TriggerMomentRecord` — the trigger moment is pinpointed to observation index, block number, timestamp, window slice, and on-chain receipt.

## ⚠️ Clearly Stated Limits & Architectural Boundaries

**Scope & semantics**
- The watcher observes **one metric of one watcher per rule**. It is a *guard/monitor* skill, not a general-purpose trading bot: the "protective action" is an on-chain proof-anchor (plus whatever execution hooks are wired into the injectable `ActionExecutor`), not a full rebalancing engine.
- Metric support today: synthetic values, ERC-20 balances, native balance. Price-oracle feeds would plug in via the same `metricSource` mechanism but are not bundled.
- `requiredObservations >= 3` is enforced **everywhere** (store construction, CLI, API, UI) — a single observation can never authorize an action, by design.

**Storage & crash model**
- State is per-machine disk storage (`.data/`), not a replicated database. Cross-machine HA, file locking across *concurrent* writers, and multi-node coordination are out of scope; writes are atomic (tmp+rename+fsync) and appends are fsync'd, which makes the common cases (one writer, crash-restart cycles) safe — verified by tests.
- The WAL is append-only and replayed fully on load; it is not compacted (bounded by observation count per watcher).
- The keccak hash chain commits `(prevHash, blockNumber, value, observationId)` where `observationId` commits the canonical **60 s bucket**. Sub-bucket timestamp drift is therefore idempotency-tolerated *by design* (a re-poll of the same window is the same observation) and is **not** part of the tamper envelope — documented and tested explicitly in `tests/storage.test.ts`.
- If the hash chain IS broken (any tampering of committed fields), the store refuses to observe or act (`StoreIntegrityError`, HTTP 409) — it never silently "repairs".

**On-chain layer**
- Phase C's falling metric is produced by real dust USDC drains from the watched vault (burnable testnet funds, ≤ 0.0005 USDC per run); this keeps the observation genuinely live rather than mocked.
- Pharos Atlantic's RPC occasionally fails `eth_call` against freshly-written contract state (observed during verification: "undefined instruction" / "EVM stack" errors on struct returns). The verifier therefore proves the anchor via the **`TrendAnchored` event decoded from the tx receipt** (deterministic), with flat view getters as a best-effort secondary. `TrendAnchor.getProof()` returns a struct and may hit the same quirk on this testnet; flat getters are provided.
- The anchor contract has no access control beyond "one anchor per proofDigest" — it is a public notary, not a custody contract. It holds no funds.
- Gas/key: the bundled key is the shared **burnable Atlantic testnet** payer key from the sibling projects. Nothing here is mainnet-safe: no key rotation, no gas-price policy, no nonce-lock (concurrent writers could race nonces).

**Testing**
- `tests/cli.test.ts` spawns real processes (~60 s of the suite). On Windows, a SIGKILL'd child surfaces as `exit=1`/`signal=null` rather than `SIGKILL` — the assertion accepts both.
- UI components are exercised through build-time rendering + the API route tests, not a browser-DOM test harness.
